# Swagger / OpenAPI / RESTful API — 具体例から思想へ

このドキュメントは、このプロジェクトの実際のコードを題材に、
**「具体例（Swagger）→ 設計（OpenAPI）→ 思想（RESTful API）」** の順に抽象化しながら、3つの概念の関係を説明します。

```
[具体例]  Swagger UI        「見て・触んで分かるもの」このプロジェクトの /api-docs
   ↑ ツールが仕様を可視化・検証する
[設計]    OpenAPI          「APIの契約書」このプロジェクトの openapi.yaml
   ↑ 契約がアーキテクチャスタイルに従う
[思想]    RESTful API      「設計の原理原則」リソース・HTTP動詞・ステートレス
```

---

## 第1章：具体例 — Swagger とは「見えているもの」

### 1.1 まず触れてみる

サーバーを起動してブラウザで http://localhost:3000/api-docs を開くと、次のものが見えます。

- **エンドポイントの一覧**（`GET /tasks`、`POST /tasks`、`GET /tasks/{id}`、`DELETE /tasks/{id}`）
- **各操作の説明文**（「タスク一覧取得」「タスク作成」...）
- **リクエスト・レスポンスの形**（`title` は文字列で必須、`done` は真偽値、など）
- **Try it out ボタン**（その場で本物のリクエストを送って試せる）

これが **Swagger** の正体です。「Swagger = Swagger UI というツールの名前」であり、APIの仕様を**人間が見て・触って確認できるようにした画面**です。

### 1.2 実例：Swagger UI はどこから来ているか

このプロジェクトでは `server.js` にこう書かれています（server.js:10-13）。

```js
const spec = jsyaml.load(fs.readFileSync(path.join(__dirname, 'openapi.yaml'), 'utf8'));
app.use('/api-docs', swaggerUi.serve, swaggerUi.setup(spec));
```

注目すべきは **Swagger UI は1行もAPIを知らない** ということです。
読み込んでいるのは `openapi.yaml` という仕様ファイルだけで、UI はそれを解析して**自動的に**画面を組み立てています。

つまり：

> Swagger UI は「描画係」であり、「情報源」ではない。
> 情報源は OpenAPI 仕様（openapi.yaml）である。

### 1.3 Swaggerという言葉の整理

| 言葉 | 実体 |
|---|---|
| Swagger UI | 仕様を可視化するツール（今回 /api-docs で見たもの） |
| Swagger Editor | 仕様yamlを書きながらプレビューできるツール（editor.swagger.io） |
| Swagger 2.0 | 仕様書式の古い名称（後述のOpenAPIの前身） |

歴史的経緯：仕様書式は元々「Swagger Specification」と呼ばれていましたが、2015年にLinux Foundationへ寄贈されてオープン標準化され、 **「OpenAPI Specification」** と改名されました。以降は「Swagger＝ツール群」「OpenAPI＝仕様書式」と役割が分かれています。

## 第2章：設計 — OpenAPI とは「APIの契約書」

具体的な画面（Swagger）の裏にあった `openapi.yaml` の中身を見て、抽象度を1段上げます。

### 2.1 実例：openapi.yaml の骨格

このプロジェクトの `openapi.yaml` は、大きく3つの部品でできています。

```yaml
openapi: 3.0.3            # ┐
info:                     # │
  title: Task API         # │ ① APIのメタ情報
  version: 1.0.0          # │
servers:                  # │
  - url: http://localhost:3000
                          # ┐
paths:                    # │ ② どういう操作（エンドポイント）があるか
  /tasks:                 # │
    get: ...              # │
    post: ...             # │
  /tasks/{id}:            # │
    delete: ...           # │
                          # ┐
components:               # │ ③ データの形（スキーマ）の定義
  schemas:                # │
    Task: ...             # │
    TaskInput: ...        # │
```

### 2.2 OpenAPIの核心：HTTPをそのまま構造化している

`paths` の中を見てみましょう（openapi.yaml 抜粋）。

```yaml
paths:
  /tasks/{id}:
    get:
      summary: タスク詳細取得
      parameters:
        - name: id
          in: path           # ← パスパラメータであることを宣言
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: タスク詳細
        '404':
          description: タスクが見つからない
```

ここで定義しているのは、実はどれも **HTTPの部品** です。

| OpenAPIの項目 | 対応するHTTPの部品 |
|---|---|
| `path: /tasks/{id}` | URLのパス部分 |
| `get` / `post` / `delete` | HTTPメソッド |
| `parameters[].in: path` / `query` | パラメータの置き場所 |
| `requestBody` | HTTPリクエストボディ |
| `responses: '200'` / `'404'` | HTTPステータスコードとレスポンス |

つまり：

> **OpenAPIとは「HTTPでやり取りされる内容の全部品に型と説明を与える、標準化された書式」である。**
> 機械が読める形式（YAML/JSON）で書かれた「APIの契約書」。

### 2.3 再利用：`$ref` と `components/schemas`

`components` にデータの形をまとめ、`$ref` で参照するのがOpenAPI流の書き方です。

```yaml
paths:
  /tasks:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Task'   # ← 定義を再利用

components:
  schemas:
    Task:
      type: object
      required: [id, title, done]
      properties:
        id:    { type: integer }
        title: { type: string }
        done:  { type: boolean }
```

これの何が嬉しいか：

1. **POSTで受け取る形・GETで返す形の食い違いが構造的に起きない**（同じ定義を参照するため）
2. **仕様書に型情報が入る**ため、型クライアントコードの自動生成（TypeScript、C#など）や、モックサーバーの自動生成に使える
3. **Swagger UIはこの構造を解析して**、フォームやサンプル値を自動生成していた（第1章の「Try it out」の正体）

### 2.4 契約としてのOpenAPI

要点を1つにまとめると：

> OpenAPIは「このAPIはこういうURLにこういうメソッドでこういう形のデータをやり取りする」という**約束**を、人間と機械の両方が読める形で記述したもの。
> 実装（server.js）はこの契約を履行する手段の1つにすぎない。

だから契約（openapi.yaml）だけあれば、実装を書く前に：
- Swagger UI / Postman でAPIをシミュレーションできる
- フロントエンドとバックエンドが並行開発できる
- コード生成ツールに型を吐かせられる

## 第3章：思想 — RESTful API とは「設計の原理原則」

最後に、OpenAPIが「記述」していたその設計自体は、どこから来ているのか。RESTというアーキテクチャスタイルの考え方に到達します。

### 3.1 実例：このAPIの設計を振り返る

`server.js` の実装と `openapi.yaml` の仕様は、次のような作りになっていました。

```js
app.get('/tasks', ...)          // 一覧
app.post('/tasks', ...)         // 作成
app.get('/tasks/:id', ...)      // 詳細
app.delete('/tasks/:id', ...)   // 削除
```

一見当たり前ですが、「なぜこういうURL・メソッドの組み合わせなのか？」を突き詰めると、それがRESTの思想です。

### 3.2 原則①：URLは「リソース（名詞）」を指す

`/tasks` というURLは「タスク**の一覧**というリソース」を、`/tasks/1` は「ID 1のタスクというリソース」を指しています。

- ○ `/tasks`（リソース名は名詞・複数形）
- × `/getTasks`（操作をURLに入れない）
- × `/tasks/delete/1`（削除という操作をURLに入れない）

**「何を（リソース）」と「どうする（操作）」を分離する**のがRESTの第一原則です。

### 3.3 原則②：操作はHTTPメソッド（動詞）が担う

「どうする」はURLではなくHTTPメソッドで表現します。

| HTTPメソッド | 意味 | このAPIでの例 | 冪等性 |
|---|---|---|---|
| GET | 取得（副作用なし） | `GET /tasks` | あり |
| POST | 作成 | `POST /tasks` | なし |
| PUT/PATCH | 更新 | （未実装。演習で追加するとよい） | PUTはあり |
| DELETE | 削除 | `DELETE /tasks/1` | あり |

だから `DELETE /tasks/1` は「タスク1という**リソースを消す**」と読めます。OpenAPIの `paths` 直下に `get` / `post` / `delete` が並んでいたのは、この原則を仕様書式が素直に写したものだったのです（第2章との接続点）。

### 3.4 原則③：ステートレス（状態をサーバーに持たせない）

このAPIの各リクエストは、それ単体で完結しています。

```powershell
Invoke-RestMethod http://localhost:3000/tasks/1   # ← 認証トークン等なしで1回で完結
```

サーバー側は「前回どのリクエストが来たか」を覚えていません（データがメモリにあるだけです）。
HTTPというプロトコル自体がステートレスであり、それを活かすと：

- 同じリクエストをどのサーバーに送っても同じ結果になる（**スケールアウトが容易**）
- 途中で1台落ちても、他の台が処理を引き継げる
- キャッシュやCDNが機能する（GETの結果は誰が見ても同じため）

### 3.5 原則④：ステータスコードで結果を伝える

`server.js` の実装を見ると、成功・失敗をHTTPの標準語彙で伝えています。

| コード | 意味 | このAPIでの例 |
|---|---|---|
| 200 | 成功 | `GET /tasks` の結果 |
| 201 | 作成成功 | `POST /tasks` の結果 |
| 204 | 成功（返すbodyなし） | `DELETE /tasks/1` の結果 |
| 400 | クライアントの入力が不正 | `title` が空のPOST |
| 404 | リソースが存在しない | 存在しないIDのGET |

OpenAPIの `responses: '200' / '404'` という書き方は、まさにこの「HTTPの標準語彙で結果を語る」思想の写像でした。

### 3.6 RESTful APIの本質

ここまでの原則を1つの文章にすると：

> **RESTful APIとは、「Webそのものの設計原理（Uniform Interface）に乗っかることで、APIもWebと同じようにシンプルに・スケーラブルに・進化可能に作れるようにする考え方」。**
> URLで名詞（リソース）を指し、HTTPメソッドで動詞（操作）を表現し、標準ステータスコードで結果を伝え、サーバーはリクエスト間の状態を持たない。

## 終章：3つの関係を1枚に

```
REST（思想）
  「リソースをURLで指し、HTTP動詞で操作し、状態を持たない」
        │ この原則に従ってAPIを設計する
        ▼
OpenAPI（設計・契約）
  「そのAPIを、機械可読なYAMLで標準形式の契約書に落とす」
  （このプロジェクト： openapi.yaml）
        │ この契約を入力として
        ▼
Swagger（具体例・ツール）
  「契約を人間が見て触って確認できるUIにする」
  （このプロジェクト： http://localhost:3000/api-docs）
```

| 抽象度 | 名前 | 一言 | このプロジェクトでの場所 |
|---|---|---|---|
| 思想 | RESTful API | Webの原理に乗った設計原則 | server.js のURL・メソッド・ステータスコードの作り方 |
| 設計 | OpenAPI | API契約の標準記述形式 | openapi.yaml |
| 具体例 | Swagger | 契約を可視化・検証するツール群 | /api-docs（Swagger UI） |

## 演習：3層を行き来してみる

1. **思想→設計**： `PUT /tasks/{id}`（更新）をREST原則に従って設計し、`openapi.yaml` の `paths` に追加する
2. **設計→実装**： `server.js` に `app.put('/tasks/:id', ...)` を追加して契約を履行する
3. **実装→具体例**： 再起動後、Swagger UI に `PUT` が現れることを Try it out で確認する

この一連の流れが、まさに「思想を設計に落とし、設計を実装し、ツールで検証する」API開発の基本形です。
